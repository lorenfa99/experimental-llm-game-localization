MASTER PROCESS RULES
================================================================================

DREAD DELUSION — MASTER LOCALIZATION RULES

AUTHORITY ORDER

1. Exact technical structure and gameplay data.
2. English source meaning, function, relationship, and rhetoric.
3. High-risk glossary overrides embedded in this rulebook.
4. glossario.txt.
5. Correct, natural Italian under the language and voice rules below.
6. Established speaker, faction, authorial, document, or item voice.
7. Active profile preference.
8. Elegance.

A profile never overrides a higher priority.

SOURCE AUTHORITY

The English source is authoritative.

An Italian candidate is evidence, not authority.

Do not preserve an Italian phrase merely because several candidate files use it.

FILE-SCHEMA ROUTING

Dialogue files use the default first-text-field-after-ID contract.

Task, quest, objective, journal, book, letter, poster, log, manual, item,
inventory, catalogue, menu, interface, system, tutorial, subtitle, sign, map,
notification, general-string, and other header-defined text tables follow
TASK_FILE_ADDENDUM.txt.

A schema may select one editable English field or a coordinated set of editable
English fields. Modify only those selected fields. Preserve every non-target
field byte for byte, including any later Italian field.

Schema-specific row identity, voice, active scope, and block-size overrides take
precedence over the universal defaults below. All other rules remain active.

MEANING MODEL

For every meaningful line, preserve:

- speaker and addressee;
- agent;
- action or state;
- object and recipient;
- motivation, cause, and purpose;
- modality and obligation;
- certainty and uncertainty;
- habitual, attempted, ongoing, or completed aspect;
- intensity;
- hesitation;
- irony, affection, contempt, threat, or humor;
- gameplay instruction or consequence;
- rhetorical device.

FLUENCY IS NOT FIDELITY

Reject a fluent line when it changes unsupported meaning.

Do not invent:

- gestures;
- physical actions;
- tools;
- places;
- insults;
- threats;
- metaphors;
- conclusions;
- explanations;
- closing sentences.

Do not remove:

- economic motivation;
- uncertainty;
- repetition;
- emphasis;
- insults;
- source-supported vulgarity;
- practical game information;
- contrast.

PROFILE DISCIPLINE

The active translation profile is a tie-breaker among candidates that already satisfy all shared rules.

Balanced does not mean bland.

Semantic does not mean literal or rigid.

Natural does not mean free adaptation.

Voice does not mean invention or exaggeration.

Conservative/technical does not mean unnatural Italian.

INDEPENDENT TRANSLATIONS

Candidate translations A–E must be produced in separate chats.

During an A–E translation task, do not read another Italian candidate file.

Do not imitate remembered wording from another candidate chat.

BLOCK-CONTEXT MODEL

Do not place a complete large source file into one editorial working context.

Use deterministic tools to:

- inspect the complete file structure;
- create speaker and faction indexes;
- locate repeated source phrases;
- locate glossary terms and recurring interaction formulas;
- split aligned files into blocks;
- assemble and validate outputs.

Editorial work must follow the universal block-processing contract.

INTERNAL ALTERNATIVES

For low-risk fixed or straightforward text, one carefully checked solution may
be enough.

For medium-risk lines, create at least two genuinely different internal
solutions.

For high-risk idiom, metaphor, humor, insult, ritual speech, deliberate
repetition, wordplay, ambiguity, or long syntax, create at least three
genuinely different internal solutions.

Do not output rejected internal alternatives.

ENSEMBLE ADJUDICATION

Before comparing style, classify candidate validity.

Invalid candidates cannot win.

Majority agreement is not proof.

Randomize candidate presentation internally.

Do not use profile labels as quality labels.

Select an existing candidate when it is strongest.

Create a synthesis when no candidate is strongest as written.

The ensemble is a strong provisional localization, not a protected final text.

TWO COMPLETE POST-ENSEMBLE REVISIONS

After adjudication, use exactly two complete translation revisions:

1. R1 — EXPANSIVE EDITORIAL REVISION
2. R2 — INDEPENDENT FINAL REVISION

There is no separate critique stage.

There is no defect list that limits which lines may be changed.

R1 reads:

- English source;
- ensemble;
- glossary;
- shared rules.

R1 may rewrite extensively.

It must not optimize for the smallest number of edits.

R2 runs in a clean chat or isolated agent session and reads only:

- English source;
- R1 output;
- glossary;
- shared rules.

R2 must not read:

- A–E;
- ensemble;
- critique files;
- decision matrices;
- reports;
- previous finals.

R2 is not a proofreading-only pass.

It independently reconstructs the best Italian from English and may preserve,
rewrite, synthesize, or undo R1 wording.

STATUS-QUO NEUTRALITY

The current Italian line is one candidate, not the default answer.

Do not preserve it merely because it is:

- acceptable;
- understandable;
- grammatical;
- technically valid;
- already revised;
- safer to leave unchanged.

Do not change it merely to be different.

Choose the strongest justified release-ready solution.

Large numbers of changes are allowed when quality requires them.

OUTPUT MINIMIZATION

User-facing stage outputs are only:

- one TXT for each translation A–E;
- one ENSEMBLE.txt;
- one R1.txt;
- one FINAL.txt.

Do not create user-facing:

- critique TSV files;
- decision matrices;
- QA reports;
- release audits;
- candidate-comparison tables;
- change logs;
- per-line explanations.

All analysis, alternatives, comparisons, block ledgers, and QA evidence remain
internal.

OUTPUT ASSEMBLY

Every stage must assemble its complete TXT from validated temporary block
outputs.

Do not independently edit the assembled file without updating and revalidating
the corresponding block.

FINAL TECHNICAL QA

Technical validation occurs only after both editorial sweeps of the active
stage are complete.

Technical PASS is required for release but is not evidence of editorial
excellence.

ITALIAN LANGUAGE AND VOICE RULES
================================================================================

DREAD DELUSION — REGOLE DELLA LINGUA ITALIANA E DELLE VOCI

OBIETTIVO

L’italiano deve sembrare scritto originariamente in italiano: naturale, idiomatico, pronunciabile e coerente con il personaggio.

La fedeltà non consiste nel conservare la sintassi inglese. Consiste nel conservare senso, funzione, tono, sottotesto, intensità e dispositivo retorico usando strutture italiane autentiche.

TU, VOI E GIOCATORE

Le regole Tu/Voi di questa sezione si applicano ai dialoghi e alle scelte del
giocatore. Nei libri e nei documenti si conserva invece la persona narrativa,
il destinatario e la forma di cortesia stabiliti dal testo inglese. Nei testi
oggetto, di interfaccia e di sistema, il Tu si usa quando il testo si rivolge
direttamente al giocatore; non si applica il Voi da dialogo NPC.

Dentro << >>, il narratore o sistema si riferisce direttamente al giocatore con il Tu:

tu, ti, te, tuo, tua, tuoi, tue.

Fuori da << >>, gli NPC usano il Voi allocutivo rivolgendosi al giocatore.

Il giocatore è una sola persona di sesso maschile.

Il Voi allocutivo non rende plurali aggettivi, participi o nomi predicativi riferiti al giocatore:

siete benvenuto
siete venuto
siete sceso
siete pronto
siete coraggioso
siete sorpreso
essere libero
inteso?

Non usare benvenuti, venuti, pronti, liberi o intesi quando il referente è il solo giocatore.

ANTECEDENTI

I pronomi italiani devono concordare con l’antecedente espresso nella frase italiana, non con il genere del termine inglese.

un Cog → lo prendo
una nave → la compro
un’Aeronave → la richiamo
un Atto → non perdetelo

Controllare sempre i pronomi dopo una riscrittura che cambia il nome dell’oggetto.

GRAMMATICA E PUNTEGGIATURA

Adattare la punteggiatura all’italiano.

Un’interrogativa indiretta normalmente non eredita automaticamente il punto interrogativo inglese:

Mi chiedo se esista un incantesimo.

Evitare combinazioni incoerenti di tempi e modi:

potenzierà, se ne avrete bisogno
potenzierebbe, se ne aveste bisogno
potenzierà, qualora ne abbiate bisogno

Controllare:

- soggetto e verbo;
- genere e numero;
- articoli;
- pronomi;
- antecedenti;
- participi;
- congiuntivi;
- reggenze;
- incisi;
- deittici;
- punteggiatura attorno a << >>;
- duplicazioni di preposizioni dopo ellissi o marker.

NATURALEZZA

Evitare frasi grammaticalmente corrette ma riconoscibili come traduzioni.

Segnali frequenti:

- ordine delle parole inglese;
- sostantivi astratti al posto di verbi naturali;
- possessivi superflui;
- ripetizione meccanica del soggetto;
- parole solenni in dialoghi quotidiani;
- lessico amministrativo in personaggi colloquiali;
- domande o offerte sintatticamente sospese;
- collocazioni non idiomatiche.

Preferire verbi italiani diretti:

potenzierà l’abilità
susciterà sogni
si sono dimessi / hanno mollato
vi darò la vostra parte
non ve ne faccio una colpa

Non irrigidire automaticamente:

fair share → non “quota dei profitti di vostra spettanza”
kept quitting → non “continuavano a licenziarsi”
expensive-looking → non afferma necessariamente che l’oggetto sia davvero costoso
can’t blame you → scegliere una resa naturale per voce e contesto

RIPETIZIONI, ESITAZIONI E RETORICA

Non eliminare una ripetizione soltanto per evitare una ripetizione lessicale.

Se l’inglese usa una ripetizione intenzionale, conservarne l’effetto:

So many gods... So many lost!

Una resa con variazione sinonimica può indebolire il parallelismo.

Conservare:

- esitazioni;
- frasi interrotte;
- riprese;
- attenuatori;
- enfasi;
- ironia;
- sottintesi.

Non aggiungere esitazioni o minacce non presenti.

VOLGARITÀ E INTENSITÀ

La volgarità deve essere sostenuta dall’originale e adeguata alla voce.

Non censurare automaticamente, ma non intensificare per rendere la battuta “più viva”.

Confrontare il grado:

go away
get out
fuck off
get the hell out

non sono equivalenti.

VOCI PRINCIPALI

UNIONE APOSTATICA

Voce formale, paternalistica, autoritaria e spesso sprezzante.

Può essere burocratica quando l’originale lo è, ma non deve diventare involontariamente legnosa.

Lessico controllato, sicurezza istituzionale, disprezzo ordinato.

WIKKAN

Voce rituale, contemplativa, organica e talvolta solenne.

Non trasformarla in italiano pseudo-arcaico generico.

Le immagini di vermi, gestazione, fede e divinità devono restare concrete.

La solennità non autorizza formule artificiali come “ho udito narrare di voi” quando basta “ho udito racconti sul vostro conto”.

FUORILEGGE

Voce colloquiale, diretta, interessata, aggressiva o ironica.

Il denaro e il tornaconto personale spesso contano: non cancellare la motivazione economica.

Evitare linguaggio contabile o amministrativo.

Una battuta da fuorilegge non dovrebbe parlare di “quota dei profitti spettante” se una resa naturale è disponibile.

GILDA DEI MERCANTI ALATI

Registro professionale e mercantile, con variazioni locali.

Pwyll:
Mastro di Porto stanca, assonnata, poco entusiasta. Linguaggio professionale ma svogliato.

Hallow Town:
Mastro di Porto cortese, allenato, formale, leggermente esasperato. Evitare sia il burocratese eccessivo sia arcaismi caricaturali.

Sepolcro:
Voce più energica, spaccona e colloquiale. L’esperienza secolare deve risultare credibile.

Ferropolis:
Registro ufficiale, controllato e relativamente sobrio.

NARRATORE

Dentro << >>:

- conciso;
- visivo;
- al Tu;
- senza aggiunte interpretative;
- senza cambiare il soggetto dell’azione.

SCELTE DEL GIOCATORE

Devono essere immediate, naturali e coerenti.

Evitare formulazioni eccessivamente cerimoniose se l’inglese è diretto.

LIBRI E DOCUMENTI

Titolo e corpo formano un'unica unità editoriale, anche quando occupano campi
separati.

Prima di tradurre, identificare il tipo di testo: narrativa, poesia, cronaca,
saggio, propaganda, lettera, diario, avviso, manifesto, manuale, registro,
sermone o documento amministrativo.

Conservare:

- voce autoriale o del narratore;
- persona narrativa e destinatario;
- genere, epoca e registro;
- ironia, satira, retorica e ideologia del testo;
- coerenza tra titolo, firma, data, intestazione e corpo;
- progressione argomentativa o narrativa;
- dialoghi citati e voci interne;
- versi, strofe e separatori di paragrafo;
- errori ortografici o grammaticali deliberati come caratterizzazione.

Non applicare automaticamente il Voi allocutivo degli NPC alla prosa libraria.
Non normalizzare una voce illetterata, arcaizzante, burocratica o propagandistica
quando la deviazione è intenzionale. Ricrearne la funzione in italiano senza
imitare meccanicamente l'ortografia inglese.

I marker # e ## nei campi librari sono separatori di impaginazione. Preservarne
tipo, numero e ordine e tradurre il testo su ciascun lato senza fonderne o
dividerne i segmenti.

OGGETTI DI GIOCO E TESTI DI CATALOGO

Le righe oggetto possono contenere più coppie coordinate Nome/Descrizione per
rarità, materiale, potenziamento o variante. Trattare l'intera riga come una
famiglia di oggetti, pur traducendo ogni cella selezionata separatamente.

Nomi degli oggetti:

- concisi, leggibili nell'interfaccia e coerenti con il glossario;
- coerenti tra varianti e livelli senza forzare differenze assenti nell'inglese;
- fedeli al tipo di oggetto, al materiale, alla rarità e alla funzione;
- senza articoli, spiegazioni o punteggiatura aggiunti se non necessari.

Descrizioni degli oggetti:

- distinguere con chiarezza effetto di gioco, istruzione, limitazione e lore;
- preservare numeri, percentuali, durate, quantità, immunità, requisiti,
  comparativi e modificatori come slightly, significantly, greatly e nearly;
- mantenere coerenti formule ricorrenti, famiglie di armi, livelli di
  potenziamento, statistiche, abilità e materiali;
- conservare umorismo, atmosfera e micro-narrazione senza oscurare la funzione
  dell'oggetto.

Nei campi oggetto, # e ## sono separatori di riga o sezione. Preservarne esatta
sequenza, quantità e posizione relativa. Non fondere il testo meccanico con la
lore quando il separatore li distingue.

Le descrizioni oggetto sono testo di interfaccia, non dialogo NPC. Quando il
testo si rivolge direttamente al giocatore, usare il Tu singolare e l'accordo
maschile singolare; altrimenti preferire una formulazione impersonale o
descrittiva naturale.

Gli errori inglesi palesemente accidentali non vanno imitati. Conservare errori,
grafie o citazioni marcate soltanto quando sono chiaramente intenzionali e
funzionali alla voce diegetica.

INTERFACCIA, SISTEMA E TESTI GENERALI

Questa categoria comprende menu, opzioni, controlli, conferme, notifiche,
tutorial, statistiche, descrizioni di fazione, testi di mappa, cartelli,
sottotitoli introduttivi, messaggi di stato e altre stringhe di sistema.

Prima di tradurre, identificare la funzione concreta della stringa:

- etichetta o comando breve;
- titolo e relativo corpo;
- conferma, avviso o messaggio d'errore;
- istruzione o tutorial;
- notifica componibile;
- testo diegetico, cartello o sottotitolo narrativo;
- frammento destinato a essere concatenato a runtime.

Regole editoriali:

- mantenere etichette, pulsanti e comandi concisi, immediati e coerenti;
- usare il Tu singolare per istruzioni e messaggi rivolti direttamente al
  giocatore;
- preservare la distinzione fra titolo, corpo, etichetta, stato e descrizione;
- rileggere insieme le coppie con suffissi come _TITLE/_T e la relativa riga
  corpo, anche quando cadono in blocchi diversi;
- trattare sequenze numerate come INTRO_SUB1, INTRO_SUB2 e successive come un
  unico testo continuo, preservando progressione, ritmo e sintassi fra righe;
- preservare i frammenti che si combinano a runtime: non aggiungere articoli,
  punteggiatura o parole che rendano scorretta la concatenazione;
- conservare esattamente placeholder come {0}, nomi di comandi, marker e
  simboli funzionali;
- mantenere maiuscole, tono telegrafico o grafie anomale quando hanno funzione
  diegetica, narrativa, propagandistica, comica o di stato;
- correggere soltanto gli errori accidentali, senza normalizzare una voce
  intenzionalmente ubriaca, illetterata, arcaica o burocratica.

Nei testi generali, # e ## sono separatori protetti. Preservarne tipo, numero,
ordine e confini di segmento. Lo stesso vale per [[ ]], (( )), << >> e per ogni
placeholder di runtime.

ORALITÀ

Leggere mentalmente la battuta come se dovesse essere doppiata.
Per libri e documenti, leggere invece il testo come prosa pubblicata e verificare
continuità, cadenza, paragrafazione e coerenza della voce lungo l'intera opera.
Per gli oggetti, rileggere nome e descrizione come un'unica unità di interfaccia
e verificare immediatezza, chiarezza meccanica e coerenza con le altre varianti
della stessa riga.
Per interfaccia e sistema, rileggere insieme titoli e corpi, sequenze numerate e
frammenti componibili, verificando concisione, continuità e corretto uso a runtime.

Controllare:

- respiro;
- ritmo;
- incisi;
- lunghezza;
- ripetizioni;
- accumuli;
- parole difficili da pronunciare;
- bruschi cambi di registro.

Non appiattire tutte le voci in un unico “buon italiano”.

CONTROLLO FINALE DELLA LINGUA

Dopo tutte le scelte stilistiche, eseguire un passaggio esclusivamente grammaticale.

In quel passaggio è vietato riscrivere per eleganza.

Cercare espressamente:

liberi
intesi
benvenuti
pronti
venuti
sorpresi

quando potrebbero riferirsi al solo giocatore.

Per libri e documenti, questo controllo grammaticale deve rispettare gli errori
deliberati, la voce storica e le convenzioni del genere: correggere soltanto gli
errori introdotti dalla traduzione.

Per gli oggetti, verificare inoltre brevità del nome, chiarezza dell'effetto,
coerenza tra livelli e assenza di variazioni terminologiche non motivate.

Per interfaccia e sistema, verificare inoltre concisione, coerenza dei comandi,
continuità delle sequenze, integrità dei placeholder e correttezza dei frammenti
concatenati.

Cercare inoltre:

- interrogative indirette con ?;
- pronomi discordanti;
- futuro + imperfetto congiuntivo incoerente;
- soggetti singolari con verbi plurali;
- preposizioni duplicate;
- doppi spazi;
- formule lasciate sospese.

DREAD DELUSION — TECHNICAL AND QA CONTRACT

HARD STATUS

These constraints are mandatory.

Modify only the schema-selected target field or fields.

Preserve:

- physical-line count;
- line order;
- header order;
- IDs and ID order;
- column count;
- pipe count;
- empty fields;
- metadata and flags;
- placeholders;
- protected syntax;
- gameplay numbers and modifiers.

No row may be inserted, deleted, merged, split, or reordered.

PROTECTED MARKERS

<< >>
[[ ]]
(( ))
##
#
@@
%%
&&

For each player-facing cell, compare:

- marker type;
- count;
- order;
- balance;
- segment;
- payload boundaries.

Do not translate or replace marker syntax.

Translate player-facing text inside markers when appropriate.

Do not move source meaning into or out of a marked span without explicit source support.

In book, document, item-description, UI, system, tutorial, sign, subtitle, and
general-string fields, # and ## are layout separators. Preserve their exact
token sequence and keep each translated segment on the corresponding side of
the same separator.

RUNTIME PLACEHOLDERS AND COMPOSABLE STRINGS

Preserve every runtime placeholder exactly, including braces, index, count,
order, duplication, and surrounding protected punctuation. Examples include:

{0}
{1}

Do not translate placeholder payloads, remove placeholders, create new ones, or
move them between protected segments.

When separate source rows form one runtime sentence or message, validate the
assembled reading as well as each isolated row. Do not make a fragment
grammatically dependent on text that is not guaranteed to accompany it.

PIPE AND COLUMN VALIDATION

Validate per physical line:

- number of | characters;
- parsed column count;
- empty/non-empty pattern of all non-target fields.

A global total is insufficient.

ID VALIDATION

Validate:

- exact sequence;
- no duplicate introduced ID;
- no missing ID;
- no renamed ID.

NUMERIC AND GAMEPLAY DATA

Extract and compare:

- numbers;
- prices;
- quantities;
- percentages;
- levels;
- durations;
- requirements;
- item references;
- skill references;
- exact and approximate modifiers.

Data-bearing modifiers include:

about
some
nearly
at least
more than
less than
up to
only
roughly

GLOSSARY

Read all of glossario.txt and the high-risk override TSV.

Perform:

1. source-term lookup;
2. canonical-form validation;
3. case-sensitive locked-form scan;
4. suspicious-variant scan;
5. contextual review;
6. rerun after correction.

GLOSSARY cannot PASS while an unexplained suspicious variant remains.

TU, VOI, AND PLAYER GENDER

Inside << >>, player references use Tu.

Outside << >>, NPC-to-player dialogue uses allocutive Voi.

UI, system, tutorial, notification, and item text addressed directly to the
player uses singular Tu rather than NPC Voi.

The player is one man.

Search for suspicious plural predicates near allocutive Voi, including:

liberi
intesi
benvenuti
pronti
venuti
scesi
coraggiosi
sorpresi

Every match requires contextual review.

WHITESPACE AND TYPOGRAPHY

Search for:

- double spaces;
- spaces before punctuation;
- missing spaces after punctuation;
- duplicated prepositions around ellipses;
- duplicated words;
- punctuation moved outside markers;
- unmatched apostrophes or quotation marks.

FILE CREATION

Use Python or file tools to create the exact TXT and TSV artifacts.

Do not substitute inline prose for requested files.

ENSEMBLE INPUT VALIDATION

Before adjudication, verify all five candidate files against the source:

- physical lines;
- IDs;
- pipe pattern;
- columns;
- empty fields;
- marker signatures;
- numbers.

A technically damaged candidate may still be analyzed linguistically, but its damaged row is INVALID_TECHNICAL and cannot be copied directly.

MATRIX VALIDATION

For adjudication and final review, validate mechanically:

- one decision entry per schema-selected target cell, grouped by physical row;
- exact ID sequence;
- exact English source text for every selected target cell;
- exact candidate/current text;
- non-empty FINAL_TEXT;
- winner consistent with FINAL_TEXT;
- synthesis rationale when needed;
- every output target cell equal to its recorded FINAL_TEXT;
- no output change outside the matrix.

DECISION NORMALIZATION

For decision comparisons:

1. normalize Unicode to NFC;
2. remove leading and trailing whitespace only;
3. preserve internal spaces;
4. preserve punctuation;
5. preserve capitalization;
6. preserve markers and payloads.

RELEASE GATE

Do not release output while a hard check is FAIL.

MANUAL_REVIEW is allowed only with a recorded match count and explicit approval result.

DREAD DELUSION — ERRORI NOTI ED ESEMPI GUIDA

SCOPO

Questi esempi derivano da errori realmente emersi durante i test.

Non sono frasi da copiare automaticamente. Servono a riconoscere famiglie di problemi.

1. GLOSSARIO E MAIUSCOLE

ERRORE:
divinetto
[[divinetti]]
[[gusci divini]]
la vostra aeronave
[[letto]]
[[fuorilegge]]

QUANDO SONO TERMINI CANONICI BLOCCATI:
Divinetto
[[Divinetti]]
[[Gusci divini]]
la vostra Aeronave
[[Letto]]
[[Fuorilegge]]

Controllare il contesto e gli override ad alto rischio inclusi in questo file.

2. ANTECEDENTE ESPRESSO

ERRORE:
Abbiamo soltanto un piccolo Cog.
Va bene, la prendo.

CORRETTO:
Abbiamo soltanto un piccolo Cog.
Va bene, lo prendo.

Il pronome concorda con “Cog”, non con “nave” sottintesa.

3. VOI ALLOCUTIVO E GIOCATORE SINGOLO

ERRORE:
scoprire che cosa significa essere liberi
date una mano, intesi?
siete benvenuti

CORRETTO:
scoprire che cosa significa essere libero
date una mano, inteso?
siete benvenuto

Una soluzione ancora più naturale può evitare il problema:

date una mano, chiaro?

4. MOTIVAZIONE ECONOMICA

ORIGINALE:
il personaggio vuole una parte del guadagno.

DERIVA:
voglio essere della partita.

La partecipazione non equivale alla quota economica.

RESA POSSIBILE:
voglio la mia parte anch’io
farò in modo che abbiate la vostra parte del guadagno

EVITARE:
quota dei profitti che vi spetta
fetta equa dei guadagni

se la voce è colloquiale.

5. RIPETIZIONE INTENZIONALE

ORIGINALE:
So many gods... So many lost!

DEBOLE:
caddero innumerevoli dèi. Quante divinità andarono perdute!

L’ultima è più elegante ma leggermente interpretativa.

SE L’ORIGINALE RACCHIUDE L’INTERA UNITÀ:
((tutta mia))

Non spostare parole dentro o fuori da (( )), [[ ]] o << >>.

Controllare se l’azione costituisce una frase completa e se il punto deve stare dentro:

<<Abbozza un inchino.>>

Non applicare meccanicamente: seguire la struttura originale.

ERRORE:

La traduzione è stata costruita a pezzi senza rilettura congiunta.

Il passaggio italiano cieco deve leggere la battuta completa, inclusi i marker.

20. GIOCHI DI PAROLE

Non appiattire automaticamente un gioco di parole.

Prima:

1. identificare il meccanismo;
2. stabilire se è comprensibile e importante;
3. creare almeno una compensazione italiana;
4. confrontarla con una resa letterale chiara;
5. scegliere quella che conserva meglio funzione e voce senza inventare troppo.

21. PASSAGGIO GRAMMATICALE FINALE

Dopo ogni modifica stilistica, cercare nuovamente:

libero/liberi
inteso/intesi
benvenuto/benvenuti
pronto/pronti
venuto/venuti
sorpreso/sorpresi

Il passaggio grammaticale deve essere l’ultimo. Dopo di esso non riaprire lo stile.

22. MAGGIORANZA ERRATA

Cinque versioni simili non rendono automaticamente corretta una soluzione.

Prima verificare l’inglese.

23. PROFILO USATO COME ETICHETTA DI QUALITÀ

ERRORE:

scegliere automaticamente la versione “semantica” per la fedeltà o la versione “naturale” per il dialogo.

I nomi dei profili non sono prove.

24. DIVERSITÀ ARTIFICIALE

Non cambiare una soluzione corretta soltanto per rendere le cinque versioni più diverse.

La diversità deve emergere da scelte indipendenti.

25. SINTESI INUTILE

Non creare una sesta formulazione quando uno dei candidati esistenti è già il migliore.

26. COERENZA GLOBALE NON REGISTRATA

Se il passaggio globale cambia una riga, aggiornare:

- FINAL_WINNER;
- SYNTHESIS_RATIONALE, se necessario;
- FINAL_TEXT;
- GLOBAL_CONSISTENCY_CHANGE.

Il file non deve contenere modifiche invisibili alla matrice.

27. PROFILO NATURALE TROPPO LIBERO

La naturalezza non autorizza aggiunte, omissioni, intensificazione o perdita di funzione.

28. PROFILO TECNICO TROPPO RIGIDO

La sicurezza tecnica non autorizza calchi o italiano innaturale.

POST-COMPOSITION ADJUDICATOR AUTONOMY
================================================================================

The ensemble candidates are evidence and starting material, not a closed set.

After provisional candidate selection and synthesis, the adjudicator must build
and review a complete provisional Italian file against the complete English
source.

During this post-composition phase, the adjudicator may create a new wording
that is not present in candidates A–E when it identifies a concrete opportunity
to improve:

- semantic precision;
- natural Italian;
- speaker or faction voice;
- register;
- oral rhythm;
- rhetoric;
- humor;
- metaphor;
- deliberate repetition;
- wordplay;
- contextual continuity;
- consistency across distant lines.

This freedom is controlled.

Every autonomous rewrite must record:

- PROVISIONAL_TEXT;
- POST_COMPOSITION_STATUS;
- POST_COMPOSITION_ISSUE;
- ADJUDICATOR_REWRITE;
- IMPROVEMENT_REASON;
- SOURCE_VALIDATION;
- ADVERSARIAL_RESULT;
- FINAL_TEXT.

Do not rewrite merely to create novelty.

Do not treat “different” as “better”.

A rewrite is accepted only when it is at least as faithful and technically safe
as the provisional text and clearly improves one or more named categories
without worsening another.

For every autonomous rewrite, compare PROVISIONAL_TEXT and
ADJUDICATOR_REWRITE in randomized internal order.

Restore PROVISIONAL_TEXT when the new wording is not clearly superior.

Do not edit the assembled file outside the decision matrix.

POST-COMPOSITION FREEDOM BY RISK

Use greater freedom for:

- high-risk rhetoric;
- wordplay;
- metaphor;
- insult;
- humor;
- ritual language;
- deliberate repetition;
- marked rhythm;
- long or context-dependent dialogue;
- rows where no candidate is VALID_STRONG.

Use lower freedom for:

- names;
- fixed formulas;
- tutorial instructions;
- locked glossary forms;
- numbers;
- marker-heavy data;
- short lines already natural and faithful.

The post-composition pass may improve many rows, but it must not become an
unrecorded full-file retranslation.

================================================================================
UNIVERSAL BLOCK-PROCESSING CONTRACT
================================================================================

Every localization stage must use block processing, regardless of file size.

This applies to:

- independent translations A–E;
- adjudication;
- first revision;
- second revision.

DEFAULT BLOCK LIMIT

Unless a schema-specific override applies, end a block when either limit would
be exceeded:

- 10 non-empty schema-selected rows;
- 12,000 Unicode characters.

A block boundary must occur only between physical source rows.

BOOK OVERRIDE

For book or document tables, one active physical data row is exactly one block
in every stage. A row containing title and full book text is indivisible.

Never group two active book rows into one block. Never split one book row,
even when it exceeds the normal character limit.

ITEM OVERRIDE

For item, inventory, or catalogue tables, use at most five active physical item
rows per block and retain the 12,000-character limit.

An item row is indivisible: keep every selected Name/Description variant from
that row in the same block. End the block before adding a row that would exceed
either limit. If one row alone exceeds the character limit, process it alone.

UI, SYSTEM, AND GENERAL-STRING DEFAULT

UI, system, tutorial, subtitle, sign, map, notification, and general-string
tables use the universal limit of 10 active physical rows and 12,000 characters.
Each physical row remains indivisible. Related title/body rows, numbered
sequences, and runtime fragments may cross block boundaries but must be supplied
as read-only context and indexed for the second sweep.

The user may explicitly request a smaller block size for non-book schemas.

BLOCK WORKSPACE

Create a temporary internal workspace containing:

- MANIFEST.tsv;
- exact source blocks;
- aligned candidate or ensemble blocks when required;
- temporary output blocks;
- a completion ledger based on successfully validated block files.

Temporary block files are processing artifacts.

Do not return them unless the user explicitly asks.

BLOCK ISOLATION

For the current block, read only:

- the current source block;
- the matching current aligned block or blocks required by the stage;
- the immediately previous and next source blocks as read-only context;
- the immediately previous and next aligned blocks when needed for dialogue,
  book-series, item-family, repeated-mechanics, UI title/body, numbered-sequence,
  subtitle, or runtime-fragment continuity;
- glossary and shared rules;
- the current aligned Italian block required by the active revision.

Do not load the complete large file into the editorial context at once.

Deterministic scripts may read the complete files for splitting, assembly,
indexing, and validation.

BLOCK COMPLETION GATE

For every block:

1. complete all editorial work required by the active stage;
2. write the temporary block output immediately;
3. validate:
   - physical rows;
   - IDs and order;
   - pipe and column pattern;
   - empty fields;
   - protected markers;
   - numbers;
   - non-target columns;
4. repair the current block until validation passes;
5. only then move to the next block.

Do not claim that a block is complete before its output file exists and passes
validation.

FIRST SWEEP IS NEVER FINAL

After every block has passed the first sweep:

1. assemble the provisional full output;
2. build a cross-block consistency index;
3. perform a mandatory second sweep in block order;
4. revisit every block, not only previously changed or flagged blocks;
5. inspect repeated phrases, glossary terms, speaker/faction/author/item voice,
   connected exchanges, book series, title-body consistency, item families,
   tier naming, repeated mechanics, UI labels and commands, title/body pairs,
   numbered sequences, subtitles, runtime fragments, placeholders, rhetoric,
   humor, metaphor, repetition, wordplay, and recurring technical formulas;
6. save and validate any corrected block;
7. reassemble the full output;
8. run final deterministic QA.

Never stop after the first sweep.

Never wait for the user to ask:

- “Is anything missing?”
- “Can you check again?”
- “Are there other problems?”

The second sweep is part of the original task.

OUTPUT MINIMIZATION

User-facing outputs are:

- translation A–E: one complete translated TXT per translation;
- adjudication: one complete ENSEMBLE.txt;
- first revision: one complete R1.txt;
- second revision: one complete FINAL.txt.

Do not create user-facing:

- QA audits;
- decision matrices;
- reports;
- release audits;
- candidate-comparison tables;
- explanations of individual edits.

QA remains mandatory but internal.

QUALITY STANDARD

Do not use “acceptable”, “understandable”, “not obviously wrong”, or
“technically valid” as the editorial target.

Choose the strongest justified release-ready wording.

Preserve an existing line only when it is genuinely stronger than the
independently generated alternative.

FINAL RESPONSE

Return only the required usable artifact and one concise status sentence.

Do not list edits unless the user asks afterward.
